# Admin Guide

Подробная инструкция для администратора платформы.

## 1. Где работает администратор

Основные страницы:
- `/dev/admin` — основная панель;
- `/dev/groups` — кафедры, группы и заявки на переводы;
- `/dev/kb` — база знаний.

## 2. Что администратор делает в системе

Администратор отвечает за:
- создание и поддержку пользовательских аккаунтов;
- назначение ролей;
- операционное управление статусами пользователей;
- мониторинг проектов;
- ручную корректировку статусов проектов;
- удаление проектов и пользователей;
- контроль академической структуры.

## 3. Работа с пользователями

На странице `/dev/admin` в разделе пользователей доступны действия:
- создать студента;
- создать преподавателя;
- сменить системную роль;
- активировать или деактивировать пользователя;
- сбросить пароль;
- удалить пользователя.

Используйте это, когда нужно:
- завести новый аккаунт;
- оперативно заблокировать доступ;
- восстановить доступ через новый пароль;
- исправить ошибочно назначенную роль.

## 4. Работа с проектами

На странице `/dev/admin` в разделе проектов доступны:
- фильтр по статусам;
- поиск по названию или автору;
- наблюдение за проектом;
- ручная смена статуса;
- удаление проекта.

### 4.1 Наблюдение проекта

Режим наблюдения позволяет быстро посмотреть:
- сводку по проекту;
- участников;
- задачи;
- критерии;
- текущее состояние без перехода в рабочий интерфейс студента или преподавателя.

### 4.2 Ручная смена статуса

Администратор может вручную переводить проект между статусами.

Это нужно использовать аккуратно:
- как операционный override;
- для исправления зависшего процесса;
- для административной поддержки, если обычный flow по какой-то причине не завершился.

Важно:
- ручная смена статуса обходит обычные проверки lifecycle;
- это административный инструмент, а не штатный сценарий команды или преподавателя.

### 4.3 Когда администратору стоит вмешиваться в статус проекта

Типичные случаи:
- проект застрял в промежуточной фазе из-за технической ошибки;
- нужно вернуть операционный контроль после неудачной ручной операции;
- требуется административное решение по жизненному циклу проекта.

## 5. Работа с академической структурой

Страница: `/dev/groups`

Здесь администратор может:
- просматривать кафедры;
- просматривать группы;
- искать студентов;
- отслеживать заявки на смену группы;
- одобрять или отклонять административные заявки.

Это полезно для:
- актуализации структуры факультета;
- проверки принадлежности студентов к группам;
- сопровождения переводов между группами.

## 6. Работа с базой знаний

Страница: `/dev/kb`

Администратор может использовать knowledge base для:
- публикации внутренних инструкций;
- хранения регламентов;
- ведения справочных материалов для пользователей платформы.

## 7. На что смотреть на дашборде в первую очередь

На дашборде администратора полезно регулярно проверять:
- заблокированных пользователей;
- проекты в `REVIEW` и `GRADING`;
- проекты, застрявшие в подготовке;
- операционные сигналы, требующие ручного вмешательства.

## 8. Частые вопросы

### 8.1 Когда можно удалять пользователя?

Когда вы уверены, что аккаунт больше не нужен и это не сломает рабочий процесс команды. Для активных участников и преподавателей сначала лучше проверить их текущие проекты.

### 8.2 Когда можно удалять проект?

Когда это осознанное административное решение. Перед удалением убедитесь, что проект действительно не нужен и не находится в активной работе.

### 8.3 Почему пользователь не видит нужное действие?

Проверьте:
- системную роль;
- статус пользователя;
- project-level права;
- принадлежность к faculty, группе или самому проекту.

### 8.4 Что делать, если проект “пропал” у пользователя?

Сначала проверьте:
- статус проекта;
- видимость проекта;
- доступ пользователя;
- не был ли проект переведен или удален административно.

## 9. Полезные советы администратору

- Не меняйте статус проекта вручную без понятной причины и фиксации контекста.
- Перед удалением пользователя или проекта убедитесь, что это не рабочий активный объект.
- Если команда жалуется на “пропавший” проект, сначала проверьте статус проекта и доступ пользователя.
- Если преподаватель или студент не видит нужное действие, проверьте не только системную роль, но и project-level права.
- Используйте режим наблюдения проекта перед любыми ручными административными действиями.
